# F5 Buyer dashboards — 🟡 (F5.1 ✅, F5.2 ✅)
Order history, tracking, invoices, reorder (D5.5), company spend view (⏭ candidate). Read APIs over E2/E6/F1 contracts. Sonnet, one page per unit, E2E EN+BN; IDOR 404 on every read.

**Requirement (2026-11-13, from F3a.3):** order-confirmed emails link to `/{locale}/account/orders/{orderNumber}` — F5 must serve that route (order detail by order number, owner/company access checked).

## HANDOFF (F5.1 order history + detail, with E3.6; 2026-11-16)
**Code.** api-client `orders-model.ts` (types `OrderListItem/OrderPage/OrderDetail/SubOrder/OrderLine`; `ORDER_STATUSES` = all 15 wire statuses; `orderStatusLabelKey` (unknown -> `status_other`), `orderStatusTone`, `orderTimelineIndex` (placed/confirmed/shipped/delivered from the status alone, null for cancelled/failed/returns), `totalPages`, `clampPage`, `isValidOrderNumber`, `isOrderId`, `findOrderIdByNumber` (pages the buyer's own list, <= 5 pages), `isContractPrice`) and `orders.ts` (`list(page, pageSize)`, `get` now returns `OrderDetail`). Web: `/account/orders` (`components/orders/OrdersListView.tsx`, page in `?page=`, 20 per page, Previous/Next + "Page x of y"), `/account/orders/[orderNumber]` (`OrderDetailView.tsx`), shared `OrderParts.tsx` (status chip, totals block), `lib/orders-ui.ts` (dates in Asia/Dhaka, error classes, links). Header account menu has "My orders". Messages `Orders` en + bn (all 15 statuses plain language). Both routes are noindex and protected by the existing middleware (`/account`, returnTo kept incl. the order number).
**Behaviour.** The email link carries the ORDER NUMBER but the API takes the order ID and there is no by-number endpoint, so the detail page finds the id through `GET /orders` (newest first, 5 pages = 100 newest orders) and then `GET /orders/{id}`. Not in those pages, malformed number, someone else's order: the same friendly not-found state (nothing leaks). Network/5xx: error with Retry (never "not found"). Detail shows status + 4-step progress (no invented timestamps), `estimatedDeliveryBy` only when present ("Expected by <date>" + note that it is the legal latest date), one block per sub-order (items with SKU, qty, unit price, line total; "Your contract price (ref ...)" for `priceSource=contract`; delivery fee), PO number, totals exactly as returned (subtotal, discount only when > 0, VAT, delivery, total).
**Backend follow-ups.** (1) DONE (E3c): `GET /orders/by-number/{orderNumber}` (owner only, same rule as by-id; malformed/unknown/foreign number = identical 404), so the 5-page client lookup can go. (2) DONE (E3c): `OrderDto.shipTo`, `OrderDto.payment`, `SubOrderDto.storeName` (see docs/modules/E2.md, E3c). (3) `GET /orders` is own orders only, no company-wide view for approvers/admins. (4) `estimatedDeliveryBy` is null on `pending_payment` orders (set at confirmation, E8.3), so the line appears only after payment/approval.
**Not done.** Invoices, tracking events, cancel button (API exists: `POST /orders/{id}/cancel`), company-wide history, `viewDetails` message key is unused.
**Tests.** api-client `tests/orders-model.test.ts` (9 cases), web `src/lib/orders-ui.test.ts` (5), E2E `packages/e2e/tests/orders.mjs` (`E2E_ORDERS=1`, `npm run test:orders`): real API + scratch DB, 148 checks en+bn at 360/1280 incl. axe; only the 503 case is mocked.

## HANDOFF (F5.2 reorder / Buy again; 2026-11-17)
**Decision: no backend piece.** The quick-order validate API (D5.2) already re-checks part, status (obsolete), stock, MOQ, pack size and the CURRENT price for the signed-in buyer (contract prices included), and the order lines carry `variantId` + `sku`; the cart API takes variant id + quantity only. So the whole unit is frontend; IDOR is inherited: the panel renders only after `GET /orders/{id}` succeeded for the buyer, another user's order is the same 404 as an unknown one (checked in the E2E).
**Code.** api-client `quick-order-model.ts` (appended, pure; a separate file could not import its `formatLine` under `node --test`): `reorderWanted(order)` (one line per variant, same variant in several shipments summed), `reorderText(wanted)` (`sku, qty` per line, line N = wanted[N-1]), `planReorder(wanted, result)` (add only when the server returns the SAME variant id as the old order and the line is valid; successor/look-alike never swapped in; every wanted line lands in `add` or `skip` with a reason: notFound, obsolete, outOfStock, insufficientStock (+available), qtyExceeds, ambiguous, changed, unreadable, tooMany (> 500 lines), other), `reorderReport(plan, outcomes)`. Web: `components/orders/ReorderPanel.tsx` (client island on the order detail page: button -> validate -> `cartApi.addItem` per line, stops after a 429; report with added lines at TODAY's price ("price changed, was X" note, quantity-adjusted note), a "not added" list with a plain reason per line, cart refusals (stock, full, unavailable) listed too, "Go to cart"; result region has `role=status` (`alert` on error) and takes focus). Messages `Reorder` en + bn (before `Orders`). Guest cart merge untouched (the page is sign-in only).
**Behaviour notes.** Items already in the cart are increased by the reordered quantity (cart add semantics). Only the 4 available lines are added; nothing is silently dropped. An INSUFFICIENT_STOCK line is NOT added with the smaller available amount (the buyer decides; the text says how many are left). The panel shows on every order status, also cancelled ones. Prices of the old order are never sent.
**Tests.** api-client 184/184 (6 new in `tests/reorder-model.test.ts`), web lib 46/46, typecheck + lint exit 0, bundle budget: order detail route 141.8 kB (< 170). E2E `packages/e2e/tests/reorder.mjs` (`E2E_REORDER=1`, `npm run test:reorder`): 35/35 on scratch DB `mw_f52` (dropped), own API 5952 + CORS proxy 5953 + web 3952 built from a temporary copy (removed): 7-product order, then DB changes (price +25 %, sold out, 2 left, discontinued, pack of 5); EN 1280 + BN 360: 4 added at today's price with "was" note and 3 -> 5 note, 3 listed with reasons, cart equals the API, only text sent to validate, focus moves to the result, no overflow, axe 0 violations (before and after), 503 on the check = alert + nothing added + retry works, another account sees not found and no button, API 404 identical for foreign and unknown id. Mocked: only the 503. No backend change, so no migration, no OpenAPI regeneration.
