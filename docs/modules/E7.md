## HANDOFF (E7.1 → E7.2)
**Method:** `IInventoryService.RestockAsync(new RestockRequest(variantId, quantity, RestockReason.OrderCancelled, RestockRequest.OrderReference, orderId, WarehouseId: null, ActorUserId: staffId))` → `RestockResult(AlreadyApplied, Lines[{WarehouseId, Quantity, OnHandAfter}])`. Call it once **per order line variant** with the quantity to put back (the sum of that variant's committed holds for a full cancel).
- **Idempotency key** = (reference type, reference id, reason, variant). For a cancelled order: (`order`, order id, `OrderCancelled`, variant). Replay with the same quantity = no change, `AlreadyApplied = true`; another quantity = 409 `RESTOCK_CONFLICT`. Backstop: unique index `ux_stock_movements_reference` on (reference_type, reference_id, reason, inventory_item_id). Note for F2 returns: the cap below applies only to reference type `order`, and the key allows one `ReturnRestocked` per (order, variant); a second partial return of the same variant needs a new key design (e.g. reference `return` + return id plus an explicit warehouse, which skips the order cap) — decide in F2.
- **Warehouse rule:** orders do not record a source warehouse per line, but the order's `stock_reservations` (reference id = order id, status `fulfilled`, never deleted) do. With reference type `order` the stock goes back to those warehouses (largest open amount first) and never more than they took minus everything already put back for that order under any reason → 409 `RESTOCK_EXCEEDS_DEDUCTED`. An order whose holds are still `active` (not committed) or released has deducted nothing → also `RESTOCK_EXCEEDS_DEDUCTED`: release it with `CancelAsync(orderId)` instead (E7.3 crash window: confirmed order with an active hold → `CommitAsync` or `CancelAsync`, never restock). Other reference types go to `WarehouseId`, or to the variant's only active warehouse; several → validation error. Inactive warehouses are locked and can receive stock back. A restock never creates an `inventory_items` row.
- **Semantics:** only `on_hand` grows (never `reserved`); one transaction with row locks `FOR UPDATE` on every balance of the variant in (variant_id, warehouse_id) order, the same discipline as reserve/commit/cancel; no Redis lock (like commit/cancel). Writes a `stock_movements` row per warehouse (append-only trigger) and one `inventory.restocked` audit row (entity `product_variants`, actor = `ActorUserId` or `"system"`, quantity, reason, reference, lines). After commit: storefront stock cache invalidated + `ISearchReindexQueue` for the product. Errors: `ValidationException` (quantity 1–10,000, defined reason, reference type `[a-z_]{1,40}`, non-empty reference id, `OrderCancelled` ⇒ type `order`, `WarehouseId` not `Guid.Empty`), `KeyNotFoundException` (unknown variant, no stock record in the warehouse).
- **E7.2 must:** run the restock **after** the order transaction commits (it opens its own transaction; it throws if one is already open on the shared DbContext) — same pattern as `CommitAsync` after confirmation; a crash between the two leaves a cancelled order without restock, which E7.3 must sweep (re-run is safe: idempotent). Lock order order-row → inventory rows is fine (nothing takes inventory then order). No endpoint exists for manual corrections; G5/E7.2 add it with a permission + step-up, routed through `RestockAsync` (`Correction` / `StockReceived`, `ActorUserId` from the session).
- **Limits:** no negative movement (stock decrease) yet; `AdjustOnHand` (absolute set) is unused by any endpoint and is not audited — keep it that way or route it through the ledger. Threat model: `docs/security/THREAT_MODEL_PRICING_QUOTES_PAYMENTS_INVOICING.md` §১১ (RS1–RS6).
