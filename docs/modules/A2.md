## HANDOFF (A2.x encrypted fields never in clear in audit rows, Opus 5.5, NOT committed, no migration)
- **Rule (write side, `AuditLogSaveChangesInterceptor.AuditValue`):** every value is checked in its *column* form through its EF value converter. An encrypted column (companies bin/tin/trade_licence_no) or a value the entity already holds as ciphertext (2FA secrets) is written as `"[encrypted]"` (the name list still writes `"[REDACTED]"` first for Bin/Tin/TradeLicenceNo/BinIndex/secrets); a JSON column with encrypted members (`quote_versions.company_snapshot`, `invoices.buyer_snapshot`) is written in its stored shape (`{"name":..,"bin":"[encrypted]",..}`) with every ciphertext replaced at any depth; ciphertext inside a non-JSON value fails closed to the marker. Values without ciphertext are written as before. Accepted side effect: user text that itself starts with `enc:` is masked too.
- **Marker, not ciphertext:** the log is append-only, so a ciphertext copy could never be re-encrypted on a key rotation (the backfill rewrites only the source columns) and would keep a retired key useful forever; the G5.2b viewer never decrypts anyway. The fact of a change stays visible (the key appears in old/new values).
- **Chain:** unchanged. Rows are masked before insert, so `seal_audit_logs`, `verify_audit_chain` and `GET admin/audit/chain` work as before (the integration test seals and verifies after each case).
- **Whitelist (unit `Audit/AuditEncryptedFieldsTests.cs`):** (1) probes every converted property of the EF model with a built value and must find exactly `Company.Bin/Tin/TradeLicenceNo`, `Invoice.Buyer`, `QuoteVersion.CompanySnapshot`, and checks that the audit value holds none of the decrypted plaintext and no ciphertext but keeps the clear members; (2) source scan: every `Protect(` call in backend/src must be in the reviewed file list (4 files); (3) each reviewed property, plus `User.TwoFactorSecret` and `User.TwoFactorRecoveryCodesJson`, must have an `[InlineData]` case in integration `Security/AuditEncryptedFieldsTests.cs`, which saves it through the real interceptor (create, update and delete for companies) and searches the raw `audit_logs` text for the plain values. Mutant "no nested-snapshot handling" fails 5 tests.
- **Existing rows (owner decision A2.x-1): NOT rewritten.** The trigger refuses any change to an audit row (sealed or not), and rewriting + re-sealing would break every later hash and the chain heads already logged outside the database (the anchor): exactly the tampering the chain must expose. Affected today: only dev/test databases (pre-launch). Find them: `SELECT id, entity_name, created_at FROM audit_logs WHERE jsonb_path_exists(new_values, '$.CompanySnapshot.Bin ? (@.type() == "string")') OR jsonb_path_exists(old_values, '$.CompanySnapshot.Bin ? (@.type() == "string")') OR jsonb_path_exists(new_values, '$.Buyer.Bin ? (@.type() == "string")') OR jsonb_path_exists(old_values, '$.Buyer.Bin ? (@.type() == "string")');` (old rows use PascalCase `Bin`; new rows `bin: "[encrypted]"`). Options: (a) recommended: accept for dev (synthetic BINs) and recreate the dev DB before any real buyer data; staging/production start from this code, so nothing to do there; (b) only if real BINs ever sit in a kept log: a redaction design (chain v2 hashing a per-row content digest, so a sealed `audit.redacted` entry can null a row's values while the chain still verifies) needs one migration and its own threat-model review; not built.
- **Not changed:** `invoices.seller_snapshot` BIN/TIN/trade licence stay in clear (the seller's own published registration, not field-encrypted; the viewer hides the keys). Personal-data masking is still open (G5.2b owner decision (a)).
