# E6 Invoicing (Mushak-6.3 / 6.7 / 9.1) — 🟨 E6.1 design done, E6.2 numbering core built (2026-11-21); no invoice table yet
**Boundary:** one tax invoice (6.3) per (shipment, issuing seller), issued inside the ship transaction; gap-free number per series and fiscal year (July–June, Dhaka) from a counter row locked in that transaction (never a sequence); immutable in the DB; corrections only by credit note (6.7, four eyes, never above the original); PDF EN/BN + SHA-256 store-once; PO + quote number; VDS/AIT certificates against credit receivables; monthly 9.1 export with step-up. Not in E6: debit note 6.8, third-party seller invoices (H5), partial shipments (E6.9 after F1.4), certificate uploads (C3 + V5), EFD/IVAS.
**Design (read first):** `docs/adr/0012-invoicing-and-numbering.md` (issue moment §2, config/modes §3, numbering §4, clock + fiscal year §5, snapshot + hash §6, VAT/rounding §7, immutability §8, credit notes §9, relations §10, VDS/AIT §11, PDF §12, export §13, API §14, locks §15, tables §16, audit/retention §17, owner §18, consultant §19). Abuse cases IT1–IT17: §১৪ of `docs/security/THREAT_MODEL_PRICING_QUOTES_PAYMENTS_INVOICING.md` (rules I1–I10 in §৫); the exit tests below are those names ("ITn" = every test name in that row).
**Launch rule (owner 2026-11-20):** built to the published NBR format and flagged "consultant check before relying on it" on every PDF until the owner sets `Invoicing:ConsultantChecked`. Company BIN/TIN/trade licence/address come from config (`Invoicing:*`); Live mode refuses to start without them, so no real number is taken before they exist.
**Context pack:** the ADR section of the unit · `backend/src/Mechware.Infrastructure/Orders/OrderFulfilmentService.cs` (ship transaction) · `backend/src/Mechware.Domain/Orders/Order.cs` (order, sub-order, lines, PO, quote link) · `backend/src/Mechware.Domain/Orders/OrderPricing.cs` (line money) · `backend/src/Mechware.Domain/Companies/Company.cs` (BIN) · patterns: `backend/src/Mechware.Infrastructure/Persistence/QuoteSql.cs` (guard trigger), `backend/src/Mechware.Infrastructure/Persistence/CreditLedgerSql.cs` (deferred check at COMMIT), `backend/src/Mechware.Infrastructure/Persistence/StockMovementSql.cs` (append-only), `backend/src/Mechware.Infrastructure/Quotes/QuotePdfService.cs` + `backend/src/Mechware.Infrastructure/Quotes/QuotePdfComposer.cs` (store-once PDF, hash check), `backend/src/Mechware.Infrastructure/Credit/CreditLedgerService.cs` (`ReduceChargeAsync`), `backend/src/Mechware.Infrastructure/Workers/CreditReconciliationWorker.cs` (alert, never repair), `backend/src/Mechware.Infrastructure/Persistence/AuditChain.cs`.
**Rules:** the counter is the LAST lock of any transaction (ADR §15: `… → orders → invoices → credit → companies → promotions → invoice_number_counters`); `orders` and `invoices` rows `FOR NO KEY UPDATE`; the issue instant is the DB `clock_timestamp()` read after the counter lock; nothing slow (PDF, storage, mail) inside an issuing transaction; invoice money is copied from the order lines, never recomputed (I4); one migration per unit.

- **Allocator (ADR §4 steps 1-5):** refuses with `InvalidOperationException` when no transaction is open (writes nothing); `INSERT … ON CONFLICT DO NOTHING` (year 0, next 1) → `SELECT … FOR UPDATE` → `SELECT clock_timestamp()` (unqualified, after the lock) → `Take` → plain `UPDATE`. Raw SQL and untracked: the caller's SaveChanges never writes the counter. Clock behind (earlier instant or earlier fiscal year than `last_issued_at`) → error log `ALERT INVOICE_CLOCK_BEHIND` + `InvoiceClockBehindException` (not a DomainException, so the API answers 500 as ADR §4 says; the Architecture rule forbids non-DomainException types in Domain, hence it lives in Application). Equal instants are allowed.
- **Table `invoice_number_counters`** (migration `AddInvoiceNumbering`): PK `(seller_id, series)`, `fiscal_year` int (0 before the first issue), `next_serial` bigint, `last_issued_at` timestamptz null; FK seller RESTRICT (outgoing only; no incoming FK, so `FOR UPDATE` is safe); CHECKs: series list; state `(0, 1, null)` or `(2000-9998, ≥ 2, not null)`. Guard trigger (SQLSTATE 23000, message starts with the table name): INSERT only as `(0, 1, null)`; UPDATE only `+1` in the same year or rollover to a later year with `next = 2`; seller/series never change; `last_issued_at` never goes back; `fiscal_year` must equal the July-June year of the Dhaka date of `last_issued_at` (so a UTC-year bug fails in the DB too); no DELETE, no TRUNCATE. Migration Up → Down (to `AddReturnRequests`) → Up proven by `Migration_AddInvoiceNumbering_GoesUpDownAndUpAgain` (scratch DB `mw_e62_*`); not applied to `mechware`.
