## HANDOFF (E1.2)
**Store (`RedisCartStore`):** one hash per cart at `CartOwner.StoreKey`: `e` = ETag (128 random bits, 32 lowercase hex; random, so a cart that changes and changes back still conflicts), `v` = JSON `{schema:1, version, items[{variantId, quantity, seenUnitNetMinor}]}`. Three single-key Lua scripts (read + touch, CAS save, discard-if-unchanged): atomic, cluster-safe, no hash tag needed. `null` expected ETag = SET NX; a malformed ETag is a Conflict without a Redis call; a Conflict writes nothing (not even the TTL).
- **TTL (decided):** guest 7 d, user 30 d, sliding on every save **and** every read that finds the cart (EXPIRE inside the read script). Reason: a B2B buyer reopens a cart for days while waiting for approval without changing it; save-only sliding would expire it while in use. Matches the token being re-issued on each response.
- **Stored data is not trusted:** size checked in Lua before fetching (≤ 32 KB), strict JSON (unknown, duplicate or missing fields refused), `OrderLimits` re-checked by `RedisCartStore.Violation` (the same check on save → `ValidationException`). Unreadable → log (kind, id prefix, reason, size; never content), delete if unchanged, read as absent (otherwise `Save(null)` would conflict forever). Schema newer than this build → kept + 503 (rolling deploys); schema changes take two releases (reader first), see `SchemaVersion`.
- Redis error or timeout → `ServiceUnavailableException("CART_UNAVAILABLE")` (503), never an empty cart.

**Token (`GuestCartTokenService`):** `b64url(id 16 | expiry 8 | version 1) "." b64url(HMAC-SHA256)`, 78 chars, cookie-safe. Key = HKDF(`GuestCart:TokenKey`, "mechware/guest-cart-token/v1"); `GuestCart:PreviousTokenKeys` (comma-separated) only verify (rotation: keep the old key 7 days). `Validate`: exact length → canonical base64url → MAC with `FixedTimeEquals` over all keys (no early exit) → version → expiry (also refuses > 7 d + 5 min ahead) → non-empty id; null on anything, never throws. The id is a random v4 GUID (122 bits, not guessable); the token gives integrity, not secrecy.
**Config:** `AddCartStore(configuration, requireRealSetup)` in `backend/src/Mechware.Infrastructure/DependencyInjection.cs` (one line in `backend/src/Mechware.Api/Program.cs`) refuses startup outside Development/Testing without a key, with < 32 bytes, all-equal bytes, or the published dev key (also as a previous key). Staging: `GUEST_CART_TOKEN_KEY` required (`${VAR:?}`), given to the `api` container only; H3 card lists it. `DbBackedFactory` sets a test key for Production-like test hosts.
**Tests:** `~Mechware.UnitTests.Cart` (token: forged, every bit/char flipped, expired at the second, too-long expiry, versions, truncated, huge, non-base64, 20k random strings, rotation, other key, Cecil check for `FixedTimeEquals`; key options; limits) and `~Mechware.IntegrationTests.Cart` (round trip, stale ETag, 50 concurrent writers / 50 concurrent creators over two connections → exactly 1 wins, TTLs + sliding, 25 unreadable payloads + 7 broken key shapes → absent and discarded, newer schema → 503 and kept, user/guest keys apart, delete idempotent, Redis down → 503, Production startup refused without a real key). Mutants killed: no signature check, CAS ignoring the ETag, no expiry check, no limit re-check on load, + 7 more; 2 redundant layers survive alone (canonical re-encode, exact length) but are killed together. Threat model: `docs/security/THREAT_MODEL_PRICING_QUOTES_PAYMENTS_INVOICING.md` §৯ (CT1–CT11).

**E1.3 must:** read the token only from a `__Host-` cookie (HttpOnly, Secure, SameSite=Lax, Path=/), never from URL, body or header; re-issue it on every cart response (sliding); build `CartOwner.FromValidatedGuestToken` only from `Validate`'s result; mint `GuestCartId.New()` only on the first write, not on GET; limit new guest carts per IP (CT11); on Conflict re-read, re-apply, retry (bounded) then 409; keep prices server-side (tamper test).
**E1.4 must:** merge with `CartEngine.Merge`, CAS-save the user cart (retry on Conflict), **only then** `DeleteAsync(guest)` and expire the guest cookie, so a replayed guest token afterwards sees an empty cart (CT10); new guest id after logout. `DeleteAsync` is unconditional: a guest add racing the login can be lost; add an ETag-guarded delete if that matters.
**Owner / H3b:** Redis holding carts must not evict (`noeviction` or a dedicated instance) + `maxmemory` alert; Redis AUTH/TLS in production; `GuestCart__TokenKey` in the secret store.

## HANDOFF (E1.3)
**Endpoints** (`/api/v1/cart`, anonymous allowed, all `Cache-Control: no-store`, body limit 4 KB, response `{ data: CartView }`): `GET` · `POST items {variantId, quantity}` (adds to the line; quantity must be > 0) · `PUT items/{variantId} {quantity}` (sets; **0 removes**, as `CartEngine.Set`) · `DELETE items/{variantId}` (idempotent) · `DELETE` (clear). Unknown JSON members (price, unitPrice, total ...) are not bound and ignored. `CartView` = `lines[{variantId, sku, title, quantity, unitPriceMinor, lineTotalMinor, minOrderQty, packSize}]`, `notices[{kind, variantId, was, now}]` (kinds: `priceChanged stockReduced outOfStock unavailable belowMinimumOrder quantityAdjustedToPack`), `lineCount`, `totalQuantity`, `subtotalMinor`, `currency` (BDT), `etag`.
**Prices:** `CartCatalogReader` (reads DB fresh, same rules as checkout: active product, not deleted, active variant, `PricingEngine` quote **tax-inclusive** = retail display price; stock = on hand - reserved over active warehouses). Company/tax-exclusive pricing is not in the cart yet (the stored `SeenUnitNetMinor` holds this display price). Sellable and stock are never taken from the request.
**Revalidation:** every read revalidates (no write on GET, so a notice repeats until the buyer acts); every write revalidates first, applies the change, saves the corrected cart, and returns the notices found. Unknown, archived, draft, deleted, other seller's unpublished: **404 `NOT_FOUND`, identical body** for POST/PUT. Over stock 409 `INSUFFICIENT_STOCK`, 101st line 409 `CART_FULL`, qty > 10,000 / < MOQ / not a pack multiple 400.
**Concurrency:** write = read, apply, compare-and-set; on Conflict re-read and re-apply, 3 attempts, then 409 `CART_BUSY`. Response carries `ETag: "<etag>"` and `data.etag`. Clients need not send it; optional `If-Match` (409 `CART_CHANGED` if the cart moved) for "only if unchanged".
**Identity / cookie:** signed in (Bearer) -> `CartOwner.ForUser(principal id)`, no cookie. Guest -> only from cookie `__Host-mw_cart` (HttpOnly, Secure, SameSite=Lax, Path=/, no Domain, Max-Age 7 d), through `Validate`; bad/forged/expired = no cart, silently. Same `Secure` always as the refresh cookie (browsers accept it on http://localhost). Cookie is re-issued (fresh expiry) on every response whose cart exists; never on a read without a cart; an id is minted only by POST/PUT(qty>0) with no valid cookie.
**CT11 limit:** `GuestCartCreationLimiter`, 20 new guest carts per IP per hour (**owner-reviewable default**, config `Cart:NewGuestCartsPerIpPerHour`), in memory per API replica, 429 `RATE_LIMITED`. NAT-shared offices share it. Does not touch `Program.cs` (the general limiter still applies).
**CSRF:** the API authenticates users with a Bearer header (no ambient cookie). The only cookie-authenticated path is the guest cart; guest writes with an `Origin` header outside the CORS allow-list (`ICorsPolicyProvider`, "MechWareCors") or this API's own origin are 403 `ORIGIN_NOT_ALLOWED`; no Origin (scripts) is allowed. The refresh endpoint has no such check.
**Public-endpoint list:** 5 cart routes added to `ApiSecurityRegressionTests.PublicEndpoints` deliberately.
**For E1.4:** `Identify()` in `CartController` prefers the signed-in user over any guest cookie. On login, merge with `CartEngine.Merge` (use `ICartService`/store), then `DeleteAsync(guest)` and expire the `__Host-mw_cart` cookie (`CartController.GuestCookieName`), new guest id after logout. For the web: send `credentials: "include"` on cart calls, show `notices`, treat 404 on add as "no longer available", 503 `CART_UNAVAILABLE` as "try again" (never as empty), and do not send prices.

## HANDOFF (E1.4)
**Where:** `AuthController` calls `GuestCartHandover.OnSignedInAsync` (`backend/src/Mechware.Api/Services/GuestCartHandover.cs`) after every response that starts a session: `login` (200 only, incl. the TOTP step), `verify-otp`, `google`, `2fa/enroll/complete` **and `refresh`** (the web restores sessions with refresh on each page load, so a guest cart made before that would otherwise be stranded). `IdentityService` is untouched. The handover reads the cookie, `Validate`s it, calls `ICartMergeService.MergeAsync(userId, guestId)` (`backend/src/Mechware.Application/Cart/CartMergeService.cs`), then expires the cookie (`Set-Cookie: __Host-mw_cart=; expires=1970…; path=/; secure; samesite=lax; httponly`). Forged/expired cookie: ignored, expired, no error. **Any merge error: logged, login succeeds, cookie kept, guest cart untouched** (next login/refresh retries). `logout` always expires the guest cookie, so the next guest write mints a new id.
**Atomicity (decision, owner review):** `ICartStore.SaveMergedAsync(user, merged, expectedUserETag, guest, guestETag)` is one **two-key** Lua script: write the user cart if its ETag matches **and** delete the guest cart only if it still has the merged ETag; both or nothing. Why not "CAS then conditional delete + absorbed marker": `CartEngine.Merge` adds quantities (not idempotent; `Merge_IsNotIdempotent_SoTheStoreMustMergeAGuestCartAtMostOnce`), and with two steps a guest add in another tab between them leaves a changed guest cart whose next merge cannot tell old lines from new ones (double or lose). With one step there is no state "user saved, guest still there": a lost response, a crash or a parallel login finds the guest cart gone and merges nothing; a concurrent guest add changes the guest ETag, the commit conflicts, the service re-reads both and retries (3 attempts, then `CART_BUSY` = merge skipped, login fine). **Cost: cart keys must be on one Redis node (no Redis Cluster).** On a cluster the script fails with CROSSSLOT → 503 → merge skipped, cart kept (fail-safe, never lost). Other cart scripts stay single-key.
**Rules (engine, unchanged):** shared variants add up, capped at 10,000 (`quantityCapped` notice); user lines keep their order, new guest lines follow; a guest line that would be line 101 is left out, now with a `cartFull` notice (`CartNoticeKind.CartFull`, was = guest qty, now = 0; added in E1.4, the only engine change). Merge does not revalidate; MOQ/pack/stock/price/availability notices come with the next `GET /cart` as before.
**Response (additive):** token envelopes (`login`, `verify-otp`, `google`, `2fa/enroll/complete`, `refresh`) now carry `cartMerged: null | { lineCount, notices[{kind, variantId, was, now}] }`. Anonymous objects, so `openapi.json` does not change.
**Tests:** `~Mechware.IntegrationTests.Cart` (`CartMergeTests`, `CartMergeRedisDownTests`, `RedisCartMergeStoreTests`, 19) + 2 unit in `~Mechware.UnitTests.Cart`. Not covered by an HTTP test: `verify-otp`, `google`, `2fa/enroll/complete` (same one-line call as `login`/`refresh`, which are tested). Mutants (7/7 killed): delete before CAS, no guest-ETag check in the commit, no guest delete, cookie not expired after merge, logout not expiring it, merge error failing login, no retry.
**For the web cart UI:** after any sign-in/refresh response, if `data.cartMerged` is non-null re-fetch `GET /api/v1/cart` and show `cartMerged.notices` once (`quantityCapped`: "we capped X at 10,000"; `cartFull`: "X was not added, the cart holds 100 items"); never rely on `cartMerged` being present. Keep `credentials: "include"` on `login`, `refresh`, `logout` and cart calls so the `__Host-mw_cart` cookie travels (the API sets/clears it). After logout, do not cache the old cart view. The cart badge must re-read after sign-in.
**Owner / H3b:** confirm single-node Redis for carts (no Cluster), as above.
