No bilingual message pattern exists in the backend: issues carry a stable `Code` + English `Message`; the web translates the code. D2 resolver not used.
Constants: `MaxLines` 500, `MaxLineLength` 200, `MaxInputLength` 100,000, `MaxQuantity` 1,000,000. Over 500 content lines (blank, `#`, header lines not counted) or over the size: `InputError` TOO_MANY_LINES / INPUT_TOO_LARGE / INPUT_INVALID, no lines (D5.2 maps it to 422 "501 lines refused").
Rules (first match per line): (1) tab, else `;`, else `,` = two fields part,qty (quotes honoured, trailing empty fields ignored, >2 fields TOO_MANY_FIELDS); empty qty = QTY_MISSING; comma lines ending in a thousands number ("ABC 1,000", "ABC,1,000") = qty 1000; ending " 2,5" = QTY_NOT_INTEGER. (2) `qty x part` (x X × *, "10x LC1D09") and `part x qty`. (3) whitespace: 2+ tokens and a numeric-looking LAST token = qty, rest = part ("6ES7 214-1AG40-0XB0 5"); numeric-looking but not a positive integer = error (2.5, 0, -3), never swallowed into the part. (4) else whole line is the part, qty 1, notice QTY_DEFAULTED (line with a part and an EMPTY qty cell is the error QTY_MISSING). Known ambiguity: a part whose own last word is a number ("DR 2 5") reads 5 as qty; the buyer fixes it with a comma; also "6ES7 X 214" reads as part x qty. Header = first content line made only of part/qty words (EN, BN) skipped. Qty accepts Bangla digits and "1,000", refuses decimals; 1..1,000,000. Same exact PartKey merged (qty summed, notice DUPLICATE_MERGED with `RelatedLines`; sum over max = QTY_TOO_LARGE on the later line); O/0 look-alikes are NOT merged (distinct keys, same FuzzyKey). Codes: LINE_TOO_LONG, PART_MISSING, PART_INVALID, PART_TOO_LONG (>64 key chars), QTY_MISSING, QTY_INVALID, QTY_NOT_INTEGER, QTY_TOO_LARGE, TOO_MANY_FIELDS. Control/format chars stripped, NFC, NBSP = space; line numbers are physical.
Timing: 500 lines parse in a few ms warm (test asserts < 50 ms). Mutation-checked: trailing-qty rule off (22 tests fail), merge sum (2 fail), fuzzy key (1 fails).
