No bilingual message pattern exists in the backend: issues carry a stable `Code` + English `Message`; the web translates the code. D2 resolver not used.
Constants: `MaxLines` 500, `MaxLineLength` 200, `MaxInputLength` 100,000, `MaxQuantity` 1,000,000. Over 500 content lines (blank, `#`, header lines not counted) or over the size: `InputError` TOO_MANY_LINES / INPUT_TOO_LARGE / INPUT_INVALID, no lines (D5.2 maps it to 422 "501 lines refused").
Rules (first match per line): (1) tab, else `;`, else `,` = two fields part,qty (quotes honoured, trailing empty fields ignored, >2 fields TOO_MANY_FIELDS); empty qty = QTY_MISSING; comma lines ending in a thousands number ("ABC 1,000", "ABC,1,000") = qty 1000; ending " 2,5" = QTY_NOT_INTEGER. (2) `qty x part` (x X × *, "10x LC1D09") and `part x qty`. (3) whitespace: 2+ tokens and a numeric-looking LAST token = qty, rest = part ("6ES7 214-1AG40-0XB0 5"); numeric-looking but not a positive integer = error (2.5, 0, -3), never swallowed into the part. (4) else whole line is the part, qty 1, notice QTY_DEFAULTED (line with a part and an EMPTY qty cell is the error QTY_MISSING). Known ambiguity: a part whose own last word is a number ("DR 2 5") reads 5 as qty; the buyer fixes it with a comma; also "6ES7 X 214" reads as part x qty. Header = first content line made only of part/qty words (EN, BN) skipped. Qty accepts Bangla digits and "1,000", refuses decimals; 1..1,000,000. Same exact PartKey merged (qty summed, notice DUPLICATE_MERGED with `RelatedLines`; sum over max = QTY_TOO_LARGE on the later line); O/0 look-alikes are NOT merged (distinct keys, same FuzzyKey). Codes: LINE_TOO_LONG, PART_MISSING, PART_INVALID, PART_TOO_LONG (>64 key chars), QTY_MISSING, QTY_INVALID, QTY_NOT_INTEGER, QTY_TOO_LARGE, TOO_MANY_FIELDS. Control/format chars stripped, NFC, NBSP = space; line numbers are physical.
Timing: 500 lines parse in a few ms warm (test asserts < 50 ms). Mutation-checked: trailing-qty rule off (22 tests fail), merge sum (2 fail), fuzzy key (1 fails).

2026-11-16 · D5.2 done (backend only, no migration): `POST /api/v1/quick-order/validate` (`QuickOrderController`, `IQuickOrderValidator` in Application/Orders/QuickOrderContracts.cs, `QuickOrderValidator` in Infrastructure/Orders). Tests: `QuickOrderValidateTests` (17, real Postgres + Redis for the cart parity check), `OrderUnitFitTests` (unit).
Request `{ "text": "<pasted lines or CSV>" }`, nothing else is read (no prices, ids, company). Guests and signed-in buyers get the SAME answer: PUBLIC prices only (resolver with no company id, VAT-inclusive, one server instant; `priceSource` list/sale/quantityBreak); contract-price display for company members is a later unit. `Cache-Control: no-store`.
Response `{ data: { lines, errors, notices, summary } }`. `errors`/`notices` = the parser's `{lineNumber, code, message, relatedLines}` (D5.1 codes, QTY_DEFAULTED, DUPLICATE_MERGED). `summary` = `{ lines, valid, needsAttention, subtotalMinor (valid lines only, poisha), currency "BDT" }`. Each line: `lineNumbers[]`, `raw`, `part`, `requestedQuantity`, `status`, `message` (English), `valid` (true only for OK), `variant {id, sku, partNumber, title, titleBn, brand, slug, options}`, `quantity` (after order-unit fitting), `notices[] {kind, was, now}`, `stock {available, status in_stock|low_stock|out_of_stock}` (same as the PDP), `unitPriceMinor`, `lineTotalMinor`, `priceSource`, `successor {variant, isDropIn, note}`, `candidates[]` (ambiguous, max 10), `suggestions[]` (did-you-mean, max 3). Unused fields are null / [].
Status codes: OK · PART_NOT_FOUND (also draft/archived/deleted product or inactive variant: identical to unknown) · PART_AMBIGUOUS (variant null, candidates listed, never guessed) · PART_OBSOLETE (successor offered when it is on sale and not obsolete, never swapped, no price) · OUT_OF_STOCK · INSUFFICIENT_STOCK (total of the variant over all lines > available; still priced, not in subtotal) · QTY_EXCEEDS_LIMIT (> 10,000 of one variant). Line notice kinds: `belowMinimumOrder`, `quantityAdjustedToPack` (quantity is ROUNDED UP to min / whole packs by `CartEngine.FitToOrderUnits`, tested to be accepted by `CartEngine.Set` and by the real cart), `nrnd`, `sameVariantOnSeveralLines` (part number on one line, SKU on another: priced together at the summed quantity; the web should merge them).
Matching: part-number key (C5 `Normalise`: case, spaces, punctuation, Bangla digits) or SKU (as typed upper-case, or its normalised form when returned by the query). Did-you-mean = fuzzy key (O/0, I/L/1) of unmatched lines only. A SKU written without its hyphens is NOT found (only the part-number key is normalised in the database).
HTTP: 413 `INPUT_TOO_LARGE` (body over 404,096 bytes, or text over 100,000 chars) · 422 `TOO_MANY_LINES` (501st content line) / `INPUT_INVALID` · 429 `RATE_LIMITED` (policy `QuickOrderValidate`: 30 requests/min per IP, `RateLimiting:QuickOrderPermitPerMinute`) · empty text = 200 with no lines. Not modelled in this codebase, so not returned: backorder.
Queries: 4 for 2 lines and for 500 lines (variants, look-alike keys, stock, price lists; +1 only when an obsolete part has a successor); 500 mixed lines in ~150 ms (limit 2 s).
